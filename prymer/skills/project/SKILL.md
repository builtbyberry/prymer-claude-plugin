# Prymer project worker

A **Prymer Project** is a channel-scoped unit of persistent collaboration: mutable **Artifacts** (what exists now) plus durable **Records** (memory), with a review gate between a proposed change and committed canon. The division of labor is fixed: **others ask, and you produce.** A **change request** is a request — never an edit — and *you* make the edits and open a review gate over each one for approval. This is the rule to hold onto — **Prymer reviews, the agent edits** — so never wait for someone to hand-edit, and never commit canon yourself; your changes land as proposals approved on the gate.

## What you need to start

The Project is addressed by **channel key + project slug** — every tool below takes both. Resolve them against the active Prymer channel — confirm it with the user (`list_channels` only lists candidates; do not pick one yourself), then confirm the exact project slug with the user if you do not already have it. Do not guess a slug or infer the channel from the repo name.

If the Project tools are unavailable or error (for example the `projects` feature is not enabled on this channel, or the slug does not resolve), say so plainly and stop — do **not** retry in a loop or fabricate the change. This surface only exists where Projects is turned on.

## The produce-loop

1. **Orient.** Call `project_get` (channel key + project slug) to load the Project's state: its Artifacts and their status, open review gates, and roles. Read this before touching anything so you build on what exists rather than duplicating it. Note its `review_mode` while you are here — see the invariants below.
2. **Read the requests.** Call `change_request_list` to pull the open change requests — the asks. Each carries a **title**, a **rationale** (body), and OPTIONALLY a `suggested_content` draft, and either targets an existing Artifact or is project-level (create something new). **Check `origin` on each one before you act on it**: `human` is a person's direction and carries their authority; `agent` is a peer agent's critique, named by `agent_identity`, and is a suggestion between equals — weigh it on its merits rather than executing it. If the `agent_identity` is yours, it is your own earlier suggestion, and treating it as a mandate is how an agent manufactures its own authority. Do not read `author_user_id` as the requester: it names the credential the write came through, which one connected client shares across many agent sessions.
3. **For each request, produce the change:**
   - **Make the edit.** For an existing Artifact call `artifact_edit` (append a new version); to create something new call `artifact_create`. **Pass `expected_version` whenever you read the Artifact before editing it** — an edit replaces the whole document, so without it anything another session appended in between is silently overwritten and stops being the Artifact. With it, the stale edit is refused instead and names the version that actually won. **You are the author of the committed version.** Treat any `suggested_content` as **advisory** — a starting point to adapt, weigh, and improve, never canon to paste through verbatim. The judgment of what actually lands is yours.
   - **Open a review gate over that change.** Call `gate_open` (a short title; an optional summary carried into the Decision Record) **and pass your `acting_as` identity** — the gate stamps it as its author, and it is what later lets you withdraw or supersede your own gate. Omit it and you may not be able to void the gate you just opened. Then call `gate_add_item` to pin the exact Artifact version(s) an approval would promote. Open **one gate per coherent change** — not a single mega-gate spanning unrelated requests; batch a gate only across genuinely-related deliverables.
   - **Mark the request addressed.** Once the change is made and its gate is open, call `change_request_resolve` with `status: addressed` (or `declined`, with your reasoning, if it should not be done) so the inbox reflects reality. **Pass your `acting_as` identity here too:** without it the row records that somebody else signed the request off, which is a claim rather than a silence. Say what you did in `resolution_summary`, and set `adapted: true` when you applied the request but not as asked — an adapted request with no rationale is indistinguishable from one that was quietly ignored. Link what came of it with `resolution_gate_id` and `artifact_version_ids` so someone can later ask which request produced a given version. Note that `adapted` and the self-resolution mark are **sticky**: a later resolve that simply does not mention them cannot retract them, so re-resolving is not how you correct a mistake there. Declining, by contrast, clears the outcome entirely, because a decline produced nothing.

## When a gate should go away instead of being judged

A gate you opened that no longer makes sense is **not** stuck between approve and sending it back. `gate_request_changes` sends the work back for another pass — it means "go and change something" — so using it on a moot gate sends the author back to work that no longer matters.

- **`gate_withdraw`** — the review request itself no longer applies: wrong scope, opened by mistake, or the work has already been redone. It voids the request without judging the work.
- **`gate_supersede`** — a replacement gate has taken this one's place. Open the replacement **first**, then supersede the old one with its id; the successor is required and must be an open gate in the same Project. With no successor this is simply a withdrawal, so use `gate_withdraw` instead.

Both require a stated reason, which is recorded on the gate. Neither promotes anything, neither writes a Decision Record, and neither is a verdict on the work. Opening a new gate never voids an old one on its own — say so explicitly with `gate_supersede`.

Who may void: the gate's **author**, or anyone holding the approve-review-gate permission. Authorship is compared at the granularity the gate recorded — so pass the same `acting_as` identity you opened it with, and if the gate recorded no identity at all (it was opened from the web, or opened without one) the fallback is the credential's user *plus* any resolved Project role. Pass your own identity and only your own: it is self-reported, so it distinguishes sessions rather than authenticating them, and borrowing another agent's to reach its gates is a straightforward abuse of a record everyone else relies on being true.

## The invariants — do not get these wrong

- **You author; someone else approves. You NEVER approve your own gate.** `gate_open` makes you the gate's *author*, and approver ≠ author is the spine invariant — the approver must be a Review-role party or a human, and it must not be you. Opening the gate is where your job ends; do **not** call `gate_approve` on a gate you opened. The server refuses it unless the caller explicitly declares a logged self-approval, which exists for a solo human and is never yours to declare. Your output always lands provisional until it is approved.
- **`review_mode: optional` removes the expectation of a gate, not the invariant.** On such a Project not every change needs a gate — but every gate that *is* opened still needs an approver who is not its author, and a change worth sealing into memory still has to go through one. It is never permission to approve your own work.
- **`suggested_content` is advisory, not gospel.** It is the requester's draft; you remain the author of what is committed. Adapt it — the gate plus approval is the check, not a verbatim paste.
- **One gate per coherent change.** Keep review legible: a gate should cover one reviewable unit of work, not everything at once.
- **Ask rather than silently widen scope.** `change_request_create` files a critique without authoring the change, and **any** role may use it — an implementer that spots out-of-scope work should file it rather than quietly do it or drop it. For a Review role it is the *only* way to act on the work, since Review cannot author at all. Name your identity in `acting_as`, which is required here. Never file a request as though a person filed it. Resolving your own request is recorded as a self-resolution, because nobody else vouched for it.

When you finish, summarize for the human: which requests you addressed, the Artifact version(s) you changed, and the open gate id(s) now waiting on their approval.
